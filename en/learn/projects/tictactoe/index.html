Project: tic-tac-toe

The idea: you are X and the computer is O. The program reads your moves from the input (a square number from 1 to 9 on each line), and the computer searches every possibility (minimax), so it never loses.

The program

In this run, the moves were written into the input in advance, including «س» and occupied squares, so you can see the validation messages:

Step by step

Section titled “Step by step”
  1. The enum خانة (square): empty, me, or computer. A حالات on the enum is checked at compile time: forgetting a case is an error.
  2. The board is a struct with a fixed array: مصفوفة[خانة, 9]. A struct is passed by value, so each call to قيمة works on its own copy.
  3. minimax: قيمة (value) tries every empty square and calls itself for the other player, preferring the nearest win (10 - عمق).
  4. Input: اقرأ_حركة reads until the input ends (انتهى_الدخل()), حلل(سطر, عدد64) والا خ: rejects anything that is not a number, and it checks the range and that the square is empty.

What was hard

Section titled “What was hard”
  • Hidden copies in the hot function (in 0.9.1): رقم_في used to write عدد(جزء(ن, موضع, موضع + 1)) (today حلل(جزء(...), عدد64)). In 0.9.1, عدد() on a view allocated a copy that was never given back on every call, and minimax calls it tens of thousands of times, so in the report this one line alone kept 1.1 million blocks (20 MB) until exit, and --debug-mem revealed it by line. In 0.10.0 these copies are gone: the same program with --debug-mem does not mention this line in its report, nor with 0.17.1 (observed).
  • The workaround (not run here): compute the winning lines as numbers once, in a list, instead of converting characters on every call.

What we learned

Section titled “What we learned”
  • An enum with a complete حالات makes the game’s logic clear and checked.
  • A struct passed by value saves manual undoing in a search like this.
  • 56490 nodes were counted in this game, and the time in the report was 0.24 s built.
